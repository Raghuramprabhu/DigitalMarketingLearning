    A story in six acts · with playgrounds

    Ten days in April
    that changed how the world saves its work.

    In 2005, the biggest open-source project on Earth lost its tools overnight. Its creator got angry, went quiet, and came back with something so simple and so strange that today nearly every programmer alive uses it.

    This is that story. Then we open the machine, invent it again from scratch, and learn every important command by watching what happens underneath.

    ACT I
    
      
    The Information Manager from Hell
    
      
    How do thousands of strangers, on every continent, edit the same 6 million lines of code without destroying each other's work?
    
    
    

    
    
      
    
        
    AUGUST 1991 · HELSINKI
    
        
    A student posts a hobby project
    
        
    
          
    A 21-year-old named Linus Torvalds announces a free operating system kernel, "just a hobby, won't be big." It becomes Linux. Within a few years, thousands of people are sending him improvements.
    
          
    And here's the part that sounds insane today: for ten years, there was no version-control tool at the heart of it. People emailed patches (text files listing "remove this line, add that line"). Linus read them, applied them by hand, and published the result as a .tar.gz archive.
    
          
    Linus was the version control system. A human merge machine.
    
          
    He once joked that only wimps use tape backups; real men upload their stuff to FTP and let the rest of the world mirror it.
    
          
    Hold on to that joke. "Let the world keep copies" is the seed of everything that follows.
    
        
    
      
    

      
    
        
    1972 → 2000 · THE ANCESTORS
    
        
    Tools existed. Linus hated them.
    
        
    
          
    
            
    1972SCCSBell Labs. One file at a time.
    
            
    1982RCSStores changes as backward diffs.
    
            
    1990CVSMany files, one central server.
    
            
    2000SVN"CVS done right." Still central.
    
          
    
          
    They all shared one idea: a single central server is the truth. You check out, edit, check in. No network? No history, no commits. Server dies? Everybody stops.
    
          
    For a project like Linux, with no office, no company and no single owner, that was a terrible fit. Linus considered CVS so badly designed that he preferred emailed patches.
    
        
    
      
    

      
    
        
    FEBRUARY 2002 · THE DEAL
    
        
    A free license with strings attached
    
        
    
          
    A company called BitMover, led by Larry McVoy, made BitKeeper: a genuinely distributed tool where every developer had a full copy of the history. It was proprietary, but McVoy offered the kernel community a free license.
    
          
    The catch: if you used the free version, you were not allowed to work on a competing version-control tool.
    
          
    Free-software purists were furious. Using closed software to build the most famous open project in the world? But Linus was pragmatic: it worked. For three years kernel development flew faster than ever.
    
        
    
      
    

      
    
        
    APRIL 2005 · THE TELNET INCIDENT
    
        
    Someone typed "help"
    
        
    
          
    Andrew Tridgell, the brilliant Australian behind Samba, wanted to write a free client that could talk to BitKeeper servers. How do you learn a secret protocol? He connected to a BitKeeper server with plain telnet… and typed help.
    
          
    
          
    The server politely listed its own commands. McVoy saw it as reverse-engineering in breach of the deal and withdrew the free license. Overnight, the Linux kernel, one of the most important pieces of software on Earth, had no version control.
    
        
    
      
    

      
    
        
    3 APRIL 2005 · DAY ONE
    
        
    Linus stops working on Linux
    
        
    
          
    He looked at every alternative and rejected them all. So he decided to write his own, with three rules that read like a grudge:
    
          
    
            
    🙃Do the opposite of CVSUse CVS as an example of what not to do. When in doubt, choose the exact opposite.
    
            
    🌍DistributedEvery developer has the full history. No central boss.
    
            
    🛡️Corruption-proofStrong protection against damage, accidental or malicious.
    
            
    ⚡Absurdly fastApplying a patch should take at most ~3 seconds. (He needed to apply hundreds a day.)
    
          
    
        
    
      
    

      
    
        
    7 APRIL 2005 · DAY FOUR
    
        
    Git tracks itself
    
        
    
          
    Four days after starting, Git was "self-hosting": the source code of Git was stored in Git. The very first commit is still there today, in every copy of Git's repository. Its message calls Git "the information manager from hell."
    
          
    Ever since, that first commit has kept the same 40-character name. Look at the terminal at the top of this page: that yellow hash is real. (Try clicking it.)
    
          
    
            
    18 AprFirst merge of multiple branches
    
            
    16 JunLinux 2.6.12 released, managed by Git
    
            
    26 JulLinus hands Git to Junio Hamano
    
            
    21 DecGit 1.0 released
    
          
    
          
    Linus wrote the core, then handed it over after less than four months. Junio Hamano, a quiet engineer from Japan, has stewarded Git for well over a decade since. Linus has said that much of the credit for what Git became belongs to Junio.
    
          
    Fun twist: the same month, Matt Mackall started Mercurial for the exact same reason. Two siblings, born of one feud.
    
        
    
      
    
    
    

    
    
      
    Why is it called "git"?
    
      
    tap to reveal
    
      
    In British slang, a git is an unpleasant, stubborn person. Linus joked that he's an egotist who names all his projects after himself: first Linux, now git. The original README offers more meanings depending on your mood: "global information tracker" when it works, and something unprintable when it breaks. It also calls Git "the stupid content tracker." Remember that word, stupid. It's the key to everything in Act III.
    
    
    

    
    
      
    Why "distributed" mattered
    
      
    Kill the server. See who survives.
    
      
    Old tools kept history in one place. Git gives every laptop the entire history. Try it: pick a world, then destroy the server.
    
    
    
    
    
      
    Centralized vs distributed
        
      
    
      
      
    
        
        
        
      
    
      
    Each laptop is a developer. The box in the middle is the server.
    
    
    

    
    
      
    
        
    2008 → TODAY · THE TAKEOVER
    
        
    From kernel tool to the world's default
    
        
    
          
    April 2008: GitHub launches, turning Git repositories into a social network. 2017: Microsoft moves the entire Windows codebase (about 300 GB, 3.5 million files) into Git. 2018: Microsoft buys GitHub for $7.5 billion.
    
          
    February 2017: Google and CWI Amsterdam produce the first real SHA-1 collision, two different PDFs with the same hash. Git, which names everything by SHA-1, hardens itself to detect such attacks and later adds a SHA-256 mode. (You'll see why that matters in Act III.)
    
          
    
            
    ~94%of developers use Git (Stack Overflow survey, 2022)
    
            
    100M+developers on GitHub by 2023
    
            
    10 daysfrom first line to self-hosting... well, four
    
          
    
        
    
      
    
    
    

    
    🧠 Recall before you scroll on
    
    
    
      
    What did Linux use for version control in its first 10 years?
    Nothing formal. Emailed patches + Linus applying them by hand + tarball releases.
    
      
    What single event forced Git into existence?
    BitKeeper's free license was withdrawn (April 2005) after Tridgell's reverse-engineering, the famous "telnet + help" moment.
    
      
    Linus's design rule about CVS?
    Take CVS as an example of what NOT to do. When in doubt, make the opposite decision.
    
    
    

    
    Linus called Git "stupid." Not modest; literally stupid, by design. What could a stupid tracker possibly be doing that the clever ones couldn't? You're going to find out by inventing it yourself.
    
  
    

    



    
  
    
    
    
      
    ACT II
    
      
    Invent Git Yourself
    
      
    Forget everything. You're writing a novel and want to keep every version safe, and later share it with a co-author. Let's design a tool from first principles. Four attempts.
    
    
    

    
    
      
    
        
        
        
        
      
    

      
    
        
    Attempt 1: just copy the folder
    
        
    Every time you finish a chapter, zip the whole folder. Simple, and it's what everyone does first.
    
        
    
        
    Problems: 50 versions × 200 MB = 10 GB of mostly identical bytes. No record of why anything changed. And when your co-author sends novel_FINAL_meera.zip, how do you combine her edits with yours?
    
        
      
    

      
    
        
    Attempt 2: store only the differences
    
        
    Keep version 1 in full, then store each later version as a diff: "line 40: delete; line 41: insert 'It was raining.'" Tiny! This is how RCS, CVS and SVN think.
    
        
    
        
    
        
    Problems: to see version 100 you must replay 99 diffs. One flipped bit in diff #3 silently poisons every version after it, and nothing tells you. And the diffs live on one central server.
    
        
      
    

      
    
        
    Attempt 3: snapshots named by fingerprints
    
        
    Here's the "stupid" idea. Store every file in full, but name each one by a fingerprint of its content: a hash. Identical content → identical name → stored once. Then a snapshot is just a list of fingerprints. And each snapshot records the fingerprint of the snapshot before it.
    
        
    
        
    Look what falls out for free:
    
        
      
          
    • Deduplication: 50 snapshots where chapter 1 never changed? Chapter 1 is stored once.
      • 
          
    • Instant comparison: two files differ? Compare 40 characters, not 40 MB.
      • 
          
    • Tamper-evidence: change one comma in an old chapter and its fingerprint changes, so the snapshot's fingerprint changes, so every later snapshot's fingerprint changes. Corruption can't hide.
      • 
        
    
        
      
    

      
    
        
    Attempt 4: no boss
    
        
    Because names come from content, any two computers can sync just by comparing lists of names. "I have a1b2, c3d4, e5f6. You?" "I'm missing e5f6." Send one object. Done. Nobody needs to be "the server." Everyone holds the full history.
    
        
    💻 ⇄ 💻 ⇄ 💻
    
        
    🎉
    Congratulations. You just invented Git.
    Git is a content-addressed database of snapshots (files named by fingerprints), plus a few sticky notes (branches) pointing at the latest snapshots. Everything else, every command in this page, is built on that.
    
      
    
    
    

    
    
      
    Wait. Doesn't Git store diffs? Every tool shows me diffs!
    
      
    tap to reveal
    
      
    No. Git stores snapshots. When you run git diff or look at a commit on GitHub, the diff is computed on the spot by comparing two snapshots. (Later, to save disk space, Git does compress similar objects into deltas inside "packfiles", but that's a storage trick hidden underneath. Your mental model should be: snapshots.)
    
    
    

    
    "Fingerprint of the content" sounds like magic. What exactly is being fingerprinted, and how can 40 characters stand for a whole file?
    
  
    

    



    
  
    
    
    
      
    ACT III
    
      
    Under the Hood
    
      
    Open the .git folder and you'll find a tiny, beautiful database. Seven ideas explain all of it.
    
    
    

    
    
    3.1 · Fingerprints
    SHA-1: a blender for bytes
    
      
    A hash function takes any input (a word, a novel, a movie) and blends it into a fixed 40-character fingerprint. Same input → always the same fingerprint, on every computer on Earth. Change one letter → a totally different fingerprint. You cannot run the blender backwards.
    
      
    Git doesn't hash just your file. It first glues on a tiny header: the type, a space, the size, and an invisible null byte. Type below and watch.
    
    
    
    
    
      
    🧪 Hash lab · real Git algorithm
        
        
        
      
    
      
      
      
    WHAT GIT ACTUALLY FEEDS INTO THE BLENDER:
    
      
    
      
    ⚙️ SHA-1 → the object's name
    
      
    
        
    
        
    
      
    
      
    ✅ Real Git agrees: echo hello | git hash-object --stdin prints ce01362…. Run it on any computer and you'll get the same.
    
    
    

    
    
    3.2 · The four objects
    Everything Git stores is one of four things
    
      
    Every object is saved in .git/objects/, named by its own hash. These four colours appear in every playground on this page.
    
    
    
    
    
      
    📄blobThe raw contents of one file. No name, no date. Just bytes.
    
      
    📁treeA folder listing: "name → blob hash" (or → another tree).
    
      
    📸commitA snapshot label: one tree + parent commit(s) + author + time + message.
    
      
    🏷️tagA permanent, signed-able name for a commit: "v1.0".
    
    
    
    
    💡
    Notice what a blob doesn't have: a file name. Names live in trees. That's why renaming a file costs Git almost nothing, and why two identical files anywhere in history share one blob.
    
    
    
      
    🔬 Two snapshots, side by side
        
      
    
      
      
    
    
    

    
    
    3.3 · The chain of trust
    Try to rewrite history. Quietly.
    
      
    A commit's text includes its tree's hash and its parent's hash. So each commit's fingerprint depends on everything before it. (Cryptographers call this a Merkle tree; blockchains borrowed the same trick.) Below are four real commits. Edit what the first one stored, and watch the damage spread.
    
    
    
    
    
      
    ⛓️ Tamper with commit #1
    
      
    
      
      
      
    
    
    
    
    🛡️
    That's Linus's "corruption-proof" rule, delivered by arithmetic. If you know the hash of the latest commit, you've verified the entire history behind it. And it's why the 2017 SHA-1 collision was a big deal, and why Git now detects collision attacks and supports SHA-256.
    

    
    
    3.4 · The .git folder
    The whole repository is one hidden folder
    
      
    Your project files are just a working copy. The real repository, every version ever, is .git/. Click around.
    
    
    
    
    
      
    
        
      
        
      
      
      
    
      

    
    
      3.5 · Squeezing
      zlib, then packfiles
      
      
      Each object is compressed with zlib before it's written. But imagine a 100 KB file you've edited 3 times: three nearly-identical blobs. Every so often (or when you run git gc or push), Git rolls loose objects into a packfile and stores similar objects as deltas. Plot twist: it keeps the newest version whole and the older ones as deltas, because you usually want the latest fastest.
      
    
      
    
      
      
      📦 Same three versions of style.css
      
      
      
      
      
    
      

    
    
      3.6 · Branches & HEAD
      A branch is a 41-byte sticky note
      
      
      In old systems a branch meant copying the whole project. In Git, a branch is a text file containing one commit hash. That's it. 40 hex characters plus a newline. Creating one is instant. Having 1,000 of them is fine.
      
      
      And HEAD? It's the "you are here" marker on the map. Usually it doesn't hold a hash at all: it holds the name of a branch, like ref: refs/heads/main. When you commit, Git moves the branch HEAD points to. The sticky note slides forward; HEAD rides along.
      
    
      
    
      
      
      If a branch is just a pointer, what happens to commits when you delete a branch?
      
      
      tap to reveal
      
      
      Nothing, immediately. The commits stay in .git/objects. They just become unreachable: no sticky note leads to them. Git's garbage collector only deletes unreachable objects after a grace period (typically weeks), and until then the reflog can find them. You'll use this to resurrect "deleted" work in Act V.
      
    
      

    
    
      3.7 · The three trees
      The photo studio
      
      
      Git juggles three versions of your project at all times. Think of a photo studio:
      
      
        
        
      • 📁 Working folder is the messy dressing room where people get ready. Edit freely.
        • 
        
      • 🎬 Staging area (the "index") is the stage: you choose exactly who stands in the next photo. git add puts someone on stage.
        • 
        
      • 📸 HEAD is the last photo taken. git commit clicks the shutter on whatever's on stage.
        • 
      
      
    
      
    
      
      
      
        
      📁 Working folder
      your files on disk
      
        
      🎬 Staging (index)
      .git/index: the draft of the next commit
      
        
      📸 HEAD
      the last commit
      
      
      
      
      
        
        
        
        
        
      
      
      
      All three agree: recipe v1 everywhere. Try ✏️ Edit.
      
    
      

    
      🧠 Recall
      
    
      
      
      What exactly does Git hash to name a file's blob?
      "blob" + space + size + a null byte + the file's bytes. SHA-1 of that = the blob's name.
      
      
      Name the four object types and what each holds.
      blob = file contents · tree = names → hashes · commit = tree + parents + author + message · tag = a named, annotated pointer.
      
      
      Why can't you secretly alter an old commit?
      Its hash would change, which changes its child's "parent" line, which changes the child's hash… all the way to the tip.
      
      
      What IS a branch, physically?
      A 41-byte file in .git/refs/heads/ holding one commit hash. HEAD usually points to a branch name.
      
    
      
    
      You now know the whole machine: objects, a chain, sticky notes, three trees. Every Git command is just a different way of moving those around. Let's cast some spells, and watch them work.
      
  
      

      



      
  
      
    
      
      
      ACT IV
      
      
      Everyday Spells
      
      
      Meet the cast: Paati (grandma) wrote the family recipe book. Amma improved it. Now it's yours. Your cousin Meera in Bengaluru wants to contribute too. Each command below is a chapter of their story, with a live terminal running a real Git engine.
      
    
      
    
      🕹️
      How the playgrounds work: click the glowing command chips (or type your own). The graph on top shows commits and sticky notes. The three columns are the three trees. The ⚙️ Under the hood panel narrates what Git just did internally. Click any coloured object to open it. Hashes are real SHA-1s.
      
  
      

  
      
    
      
      
      📔
      git init
      Open a brand-new diary
      
      
      Paati's recipes sit in a folder as plain files. To start keeping history, you open a diary for them. git init doesn't touch your files at all. It creates one hidden folder: .git.
      
      
      ⚙️ Under the hood
        
        
      1. Creates .git/objects/ (the database, empty) and .git/refs/heads/ (sticky notes, none yet).
        2. 
        
      2. Writes .git/HEAD = ref: refs/heads/main. HEAD points to a branch that doesn't exist yet: an "unborn branch". It's born with your first commit.
        3. 
      
      
    
      
  
      
  
      

  
      
    
      
      
      🎬
      git add
      Put someone on stage for the photo
      
      
      You've typed out Paati's rasam recipe. git add says "this goes into the next snapshot." Here's the surprise most people never learn: the file is saved into Git's database right now, at add time, not at commit time.
      
      
      ⚙️ Under the hood
        
        
      1. Reads the file, prepends blob <size>\0, computes SHA-1 → the blob's name.
        2. 
        
      2. Compresses it with zlib and writes .git/objects/ab/cdef… (first 2 hex chars = folder name). If that blob already exists, writes nothing. Free dedupe.
        3. 
        
      3. Updates .git/index: "recipe.txt → that hash." The index is literally the draft of your next tree.
        4. 
      
      
      
      Try the dedupe trick in the sandbox: copy the recipe into a second file with identical text, add it, and watch Git store nothing new.
      
    
      
  
      
  
      

  
      
    
      
      
      📸
      git commit
      Click. The photo is permanent.
      
      
      The stage is set. git commit takes the picture: a permanent snapshot with your name, the time, and a message explaining why. Commits are immutable. Not "hard to change": impossible to change, because changing anything changes the hash, which makes it a different commit.
      
      
      ⚙️ Under the hood
        
        
      1. Turns the index into a tree object (filename → blob hash list).
        2. 
        
      2. Writes a commit object: tree, parent (the previous commit), author, committer, a blank line, your message.
        3. 
        
      3. Overwrites the 41-byte file of the current branch with the new commit's hash. The sticky note moves forward. That's all "committing on a branch" means.
        4. 
      
      
    
      
  
      
  
      

  
      
    
      
      
      🔎
      git status · diff · log · show
      Spot the difference, read the diary backwards
      
      
      Amma has been editing. What changed? status tells you which files differ across the three trees. diff shows which lines. log reads the diary from newest to oldest by following parent pointers, like walking footprints backwards. You can even time-travel with git checkout HEAD~2 and look around the past.
      
      
      ⚙️ Under the hood
        
        
      1. status compares hashes: working-file hash vs index hash vs HEAD-tree hash. Equal hashes = skip. (Real Git also caches file timestamps in the index so it doesn't even re-hash unchanged files. That's why it's instant on huge projects.)
        2. 
        
      2. diff = working ↔ index. diff --staged = index ↔ HEAD. Diffs are computed live; they're never stored.
        3. 
        
      3. log starts at HEAD and follows each commit's parent line. HEAD~2 means "parent of parent of HEAD."
        4. 
        
      4. checkout <old hash> writes a raw hash into HEAD: detached HEAD. You're visiting the past without a sticky note.
        5. 
      
      
    
      
  
      
  
      

  
      
    
      
      
      🌿
      git branch · switch
      Parallel universes for 41 bytes
      
      
      You want to try a spicy rasam without ruining the family classic. Create a branch: a new sticky note on the same commit. Switch to it, experiment, commit. Switch back and the chillies vanish from your folder. Switch again and they're back. Nothing is copied; Git just rewrites the files that differ.
      
      
      ⚙️ Under the hood
        
        
      1. git branch spicy writes .git/refs/heads/spicy containing the current commit's hash. Done.
        2. 
        
      2. git switch spicy rewrites .git/HEAD to ref: refs/heads/spicy, then updates only the files whose blob hashes differ between the two snapshots.
        3. 
        
      3. If you have uncommitted edits that would be overwritten, Git refuses. It never silently destroys work.
        4. 
      
      
    
      
  
      
  
      

  
      
    
      
      
      🌊
      git merge
      Two rivers meet
      
      
      The spicy experiment was a hit. Time to bring it into main. Depending on how the histories look, Git does one of three things:
      
      
      
        
      ⏩Fast-forwardmain hasn't moved since you branched. Git just slides main's sticky note forward. No new commit at all.
      
        
      🔀Three-way mergeBoth sides moved. Git finds the merge base (last common ancestor), compares base ↔ ours ↔ theirs, and writes a commit with two parents.
      
        
      ⚔️ConflictBoth sides changed the same lines differently. Git can't read minds, so it writes both versions into the file with markers and asks you.
      
        
      🧮The ruleFor each file: if only one side changed it from base, take that side. If both changed it the same way, fine. Otherwise: conflict.
      
      
      
    
      
  
      
  
      
  
      
  
      And now the drama. You made rasam spicy on a branch, while Amma, on main, changed the same line to add drumstick. Neither of you is wrong. Git won't guess.
      
  
      

  
      
    
      
      
      🪄
      git rebase
      Rewriting your travel journal so it reads in order
      
      
      Merge keeps history honest: "these two lines of work happened in parallel, then joined." Rebase tells a cleaner story: "I started after the latest main." It lifts your commits off and replays them on top of the new base, as if you'd written them later.
      
      
      ⚙️ Under the hood
        
        
      1. Finds your commits that the target doesn't have.
        2. 
        
      2. For each one: computes what it changed relative to its old parent, applies that change on the new base, and writes a brand-new commit. New parent → new text → new hash.
        3. 
        
      3. Moves your branch to the last new commit. The originals aren't deleted; they become unreachable ghosts (watch them fade).
        4. 
      
      
      
      Below are two identical universes. Same history, same starting point. Left: merge. Right: rebase. Click both and compare the graphs.
      
    
      
  
      
  
      
    
      
      
      🔀 Team Merge

      ⚠️
      The golden rule of rebase: never rebase commits that other people already have. You'd be replacing commits they've built on with lookalikes that have different hashes. Their history and yours stop agreeing. Rebase your own unpushed work freely; merge shared work.
      

    
      
      
      🏷️
      git tag
      Carve a name into a milestone
      
      
      The recipe book is "done" for Deepavali. A tag is a sticky note that never moves. A lightweight tag is just a ref file. An annotated tag is the 4th object type: it records who tagged, when, and why.
      
    
      
  
      
  
      

      



      
  
      
    
      
      
      ACT V
      
      
      Time Travel & Safety Nets
      
      
      Mistakes happen. The surprising truth: in Git, almost nothing committed is ever truly lost. Here's how to rewind, undo, hide, copy, investigate, and resurrect.
      
    
      

    
      
      
      ⏪
      git reset
      Three rewind buttons, three levels of danger
      
      
      reset moves your branch's sticky note to another commit. The flag decides how many of the three trees get dragged along:
      
      
        
        
      • --soft: move the branch only. Your changes stay staged. ("Undo the commit, keep everything ready to re-commit.")
        • 
        
      • --mixed (default): move branch + reset the staging area. Changes stay in your files, unstaged.
        • 
        
      • --hard: move branch + staging + overwrite your files. Uncommitted work is gone.
        •

      ↩️
      git revert
      The public apology
      
      
      Last week someone committed "10 spoons of salt" and everyone already pulled it. You can't erase it (that would break everyone's history, remember the chain). Instead, you publish a correction: a new commit that does the exact opposite. History only grows. Safe for shared branches.
      
      
      ⚙️ Under the hood
      1. Takes the bad commit and its parent, computes the reverse change, applies it on top of HEAD, writes a new commit "Revert …".
      2. No commit is modified or removed. Your teammates just pull one more commit.
      
    
      
  
      
  
      

  
      
    
      
      
      🗄️
      git stash
      Sweep your half-cooked mess into a drawer
      
      
      You're halfway through a payasam recipe when Amma calls: "Urgent! Fix the rasam salt, guests are coming!" You can't commit half-written work. git stash sweeps it into a drawer, gives you a clean kitchen, and git stash pop brings it back later.
      
      
      ⚙️ Under the hood
      1. Secretly writes two commits: one for your staged state, one for your working files. Neither is on any branch; they hang off refs/stash.
      2. Resets your folder to HEAD. Later, pop three-way merges the stash back in and drops the entry.
      
    
      
  
      
  
      

  
      
    
      
      
      🍒
      git cherry-pick
      Copy one recipe card from another notebook
      
      
      Your experiments branch is a mess: a failed fusion dosa, a burnt kesari… and one gem: a perfect tempering technique. You don't want the branch. You want that one commit. Cherry-pick replays just its change onto your branch as a new commit.
      
    
      
  
      
  
      

  
      
    
      
      
      🛟
      git reflog
      The black-box flight recorder
      
      
      It's midnight. You type git reset --hard HEAD~3 by mistake. Three commits of work vanish from git log. Panic? No. Every time HEAD moves, Git writes a line in a private diary: the reflog. The commits were never deleted, just unreachable. Find the line, jump back.
      
      
      ⚙️ Under the hood
      1. .git/logs/HEAD records every HEAD movement: commits, checkouts, resets, rebases. Local to your machine only.
      2. HEAD@{1} means "where HEAD was one move ago". git reset --hard HEAD@{1} is the universal undo.
      3. Unreachable objects survive until garbage collection prunes them, by default weeks later.
      
    
      
  
      
  
      

  
      
    
      
      
      🕵️
      git bisect
      The detective who halves the suspects
      
      
      The rasam tasted perfect at Pongal. Today it's terrible. Somewhere in the last 32 commits, someone ruined it. Checking every commit means up to 31 tastings. git bisect uses binary search: taste the middle commit, throw away the innocent half, repeat. 5 tastings, guaranteed. With 1,000 commits: 10. With a million: 20.
      
    
      
    
      
      
      🕵️ 32 commits. One culprit.
      
      
      Commit 1 is known good, commit 32 is known bad. Click commits to taste them yourself, or let bisect do it.
      
      
      
      
      
    
      

    
      
      
      🏺
      git blame
      Archaeology, one line at a time
      
      
      Who added "a pinch of hing"? Blame shows, for every line, the commit and author that last introduced it. Three generations of cooks, one file. (Despite the name, it's for understanding, not for blaming.)
      
    
      
  
      
  
      

      



      
  
      
    
      
      
      ACT VI
      
      
      Many Laptops, One Story
      
      
      Meera lives in Bengaluru. The family recipe book lives on GitHub. Both of you have the entire history on your laptops. So how do you stay in sync?
      
    
      
    
      
      
      🧬cloneDownload every object, set up origin (a nickname for the server's URL), and create origin/main: a bookmark of where the server was.
      
      
      📥fetchDownload new objects and move your origin/* bookmarks. Never touches your branches or files. Always safe.
      
      
      🔄pullfetch + merge (or --rebase). This is where your work and theirs combine.
      
      
      📤pushUpload the objects the server is missing, then ask it to move its branch. It refuses if that would lose someone else's commits.
      
    
      
    
      🔑
      The mental model: origin/main is not the server. It's your laptop's last-known photo of the server. It only updates when you fetch, pull or push. That's why git status can say "up to date" while Meera pushed ten minutes ago.
      
    
      Follow the story: clone, cook, push. Then Meera pushes while you're busy, and your push gets rejected. Fix it the right way.
      
  
      
  
      
  
      
    
      💣
      git push --force tells the server "make your branch match mine, whatever it loses." If Meera's commits weren't in your history, they're gone from the server. (They still exist on her laptop, which is distributed Git saving the day.) Safer cousin: --force-with-lease, which refuses if the server moved since you last looked.
      
    
      🧠 Recall
      
    
      
      
      reset --soft vs --mixed vs --hard?
      soft: move branch. mixed: + reset index. hard: + overwrite working files.
      
      
      Shared branch has a bad commit. reset or revert?
      revert: adds an opposite commit, rewrites nothing. Safe for everyone who already pulled.
      
      
      You hard-reset away 3 commits. How to get them back?
      git reflog → find the line → git reset --hard HEAD@{n}
      
      
      fetch vs pull?
      fetch: download + move origin/* bookmarks only. pull: fetch + merge into your branch.
